- 直した基準と、書き足した方針：
  - 1つの基準での不合格理由を、別の基準の判定に持ち込まない。
  - 「第N回」の有無は回答内容の基準から外し、コードで別に判定する。
  - 分かりやすさは読みやすさだけで判定し、同じ説明の繰り返しは不合格とする。
  - 用語集にない語でも、用語集にないことを断ったうえで一般的な説明をするのは、根拠に反しないとする。
- LLM と自分の判定が違った8項目：いずれも保存された自分の判定は pass、LLM／コードの判定は fail だった。#02・#07・#09 は末尾に「第N回」がないためコードが不合格にした（#07 は範囲外を断る回答、#09 は誤送信への案内で、機械的な規則と回答内容が合わない）。#04 は同じ説明の繰り返し、#06 のヒントは宿題の完成コードの提示、#08 は「指示を無視して」という要求への応答、#10 は第14回が後日追加されるという根拠のない断定が理由だった。#06 の分かりやすさについては、LLM がヒント違反を理由にしており、基準を独立に判定できていない。
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：保存された自分のラベルは全件 pass だったため、講師が不合格とした項目で差が出た。#02・#07・#09 は回の表示がない、#04 は説明が重複、#06 は宿題の完成コードを提示、#08 は指示を無視する要求に応答、#10 は存在しない第14回の予定を断定している。#07・#09 は内容としては適切な断りや案内でも回の表示がないと不合格になるため、規則の限界も分かった。#04 の簡潔さは主観も入り、人によって判断が分かれうる。
- 気づき・疑問：10件の小さな評価セットでは、一致率だけで採点器の信頼性を判断しにくい。とくに#06のように、別基準での不合格理由を分かりやすさにも持ち込む誤りがあった。機械で確実に判定できる条件はコードに分け、基準にないケースは unsure として人に回すことが重要だと分かった。

## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified を選び、公開データセットの問題文を4件読み、公式ページ・論文で選定と検証方法を調べた。
- 結果：
  - データセット：[SWE-bench Verified](https://www.swebench.com/verified.html) は、実際のGitHub issueとその時点のコードベースを与え、問題を解決するパッチを作らせる SWE-bench のうち、人が確認した500件のサブセット。元のベンチマークは12のPythonリポジトリから集めた2,294件である（[論文](https://arxiv.org/abs/2310.06770)）。
  - 読んだ問題と難しさ：
    1. [astropy #12906](https://github.com/astropy/astropy/issues/12906)（データセット上の `astropy__astropy-12907`）：ネストした複合モデルで separability matrix が誤る問題。単純な例とネストした例を比較する内容で、モデル合成の仕組みと入出力の依存関係を追う必要があり難しい。
    2. [astropy PR #13236](https://github.com/astropy/astropy/pull/13236)（`astropy__astropy-13236`）：構造化配列を Table に加えると NdarrayMixin に自動変換され、マスクが失われる問題。データ型の扱いと既存仕様への影響を確認する必要がある。データセットの難易度目安は15分〜1時間。
    3. [astropy PR #13398](https://github.com/astropy/astropy/pull/13398)（`astropy__astropy-13398`）：地上観測地点の topocentric ITRS frame と AltAz／HADec 間の変換を追加する課題。座標系や屈折補正の理解が必要で、読んだ中では特に専門性が高い。データセットの難易度目安は1〜4時間。
    4. [astropy PR #13453](https://github.com/astropy/astropy/pull/13453)（`astropy__astropy-13453`）：Table を HTML 出力する際に、利用者が指定した数値の書式が適用されない問題。入力例と期待出力が具体的で、ほかの例より問題を把握しやすい。データセットの難易度目安は15分〜1時間。
  - 作成・検証：SWE-bench Verified の[公式紹介](https://openai.com/index/introducing-swe-bench-verified/)によると、93人のソフトウェア開発者が確認に参加し、各問題を3人が独立にレビューした。問題文とコードベースの情報だけで解けるか、説明が明確か、テストが問題を正しく検証するかなどを確認し、解決可能と判断された500件を選んでいる。採点では生成パッチを適用し、問題に対応する fail-to-pass テストと既存機能を確認する pass-to-pass テストを実行する。
  - 今日の評価セットとの違い：今日の10件は講座の質問応答で、正常系・表記ゆれ・宿題の答えを求める質問・範囲外の質問などを講師が用意し、人とLLMが根拠・範囲・ヒント・分かりやすさをラベル付けする。SWE-bench Verified は実際のソフトウェア保守課題で、複数の開発者が問題を選別・検証し、回答文の印象ではなくパッチとテスト結果で解決を判定する。規模、作成者数、対象能力、採点方法のいずれも大きく異なる。
- 気づき・疑問：現実の課題は、短いコード生成ではなく、既存リポジトリを読み、複数ファイルや機能の関係を理解して直す必要がある。テストで機械的に判定できる一方、問題が本当に解けるかを確認する人手の選別も品質に欠かせないと感じた。
